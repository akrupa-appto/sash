## Blocking requests (2026-09-19, branch todo/feat-request-queue)

- Every way a turn can stop and wait for the human lives in `extension/requests.js`, keyed by `types.js` `RequestType`. Do not add a second, parallel pause mechanism next to it.
- One turn hands back exactly one request. `pickBlocking` walks `RequestType` in its declared key order and takes the most recent of the highest-priority kind; the panel renders whatever it returns. Reordering those keys reorders the product.
- Stopping declines; it never drops. `declineAll` writes an outcome for every pending request, in the agent on abort and in the worker on a stop, a cleared chat, or a restarted worker (`expired`). Only a real refusal (`declined`, `stopped`) counts towards the denial tally.
- After `DENIAL_LIMIT` (3) refusals of the same `denialKey`, the turn ends with the cutoff message instead of asking again. The count lives in the worker's run state and is cleared when that request is finally answered.
- The credential handoff describes a form; it never carries a value. Fields are rebuilt through `credentialField`, which drops whatever the page held, so the snapshot's own values cannot travel to a model or into the run state. What the user types in the panel goes straight to `submitCredentials` and nowhere else: not persisted, not logged, not passed to the agent, which verifies from the page afterwards.
- Only whole-internet approval (`origin` absent or `*`) gets the second confirm dialog. A single-origin "always" is granted on one click on purpose.
- `panel.js` keeps one additive `renderRequest` block; `render()` was not restructured. Panel changes stay that shape.
- Still owed, per AGENTS.md: this changed the planner prompt (new `blocked_reason`, `ask`, `approve`, `credential` statuses) and has only been run against mocked planners. One real lab run before this is trusted in production.

## pr4-agent-fixes done-guards (2026-09-19, folded into the request queue below)

- The three "done" guards run in a fixed order and the order is the decision, not an accident. Guards that hand the run back to work come first (the failed-step re-check, then the "test the app" coverage floor, both of which `continue`), and only then the guard that ends the run (unsupported claims in the answer). A shallow or unconfirmed run gets a chance to earn its success; a fabricated claim never does. Same order on the planner's `done` and on jev's own `DONE`.
- A retag-retry that recovers a vanished element is not a failed step. The retry runs first in the catch block and only a still-failing action sets `pendingFailure`, otherwise every re-rendering page would end runs as unconfirmed.
- The exploratory-task check and the claim corpus both read the run's `goal`, not `input.goal`; on a resume `input.goal` is only the user's reply to what paused it.

## Unifying the two pause mechanisms (2026-09-19)

- PR #23 (`pr4-agent-fixes`, merged first) independently built a second pause mechanism: a planner `status:"question"` plus a `risk:"high"` field on `continue`, with its own `PausedRun`/resume plumbing and an `outcomeWord()` prefix ("done: …", "could not finish: …", "needs you: …") on every terminal message. PR #24's own decision above forbids a second, parallel pause mechanism, so this merge folds #23's cases into the request queue instead of keeping both:
  - `status:"question"` is gone; the planner asks with `status:"ask"` (already in this branch), which becomes a `user_input`/`option_picker` request.
  - `risk:"high"` is gone; the planner asks with `status:"approve"` (already in this branch), which becomes a three-scope `approval` request with a real button click, not a free-text "yes"/AFFIRM regex. That is a strictly stronger explicit-consent gate than #23's regex ever was ("maybe" cannot be misread as approval because there is no text reply to misread — the panel only sends `SUBMITTED` on a button click).
  - `outcomeWord()` is deleted. The panel already renders `state.status` into its own status word (`extension/panel.js` `#status-text`), so prefixing the message text duplicated that and read stiffly ("could not finish: i could not confirm this worked…"). `end()` now emits the raw message everywhere, matching what this branch already did; the two `agent.test.mjs` assertions on `/^done: /` / `/^could not finish: /` were rewritten to check the raw text.
  - What #23 had and this branch did not, preserved: the exploratory-task coverage floor (`realActions`/`pagesSeen`/`coverageRefusals`), the unconfirmed-failed-step guard (`pendingFailure`), and the stale-element retag retry. These are independent of *why* a turn pauses, so they now live on a small `PausedRun`-shaped `resume` field carried on the `needs_input` `EndEvent` (`resumeState`) and threaded back into `RunInput.resume` by `extension/background.js` on every kind of answer (ask, approve, credential) — not only #23's original question/risk pauses. A pause for a credential handoff or an approval no longer loses track of an unconfirmed failed step from earlier in the same run.
  - `panel.test.mjs`'s stale "the live action list only shows while the run is in flight" test (asserting the old "2 actions" step-count label) is deleted; #24's own log-ticker replacement test a few lines later already supersedes it.

### The tick track does not survive a real multi-step workflow (found 2026-09-20, not fixed)

Adam sent four real screenshots of the currently-installed extension running actual multi-step tasks (an X/Twitter archive workflow, ~20 actions; a search/bookmark/pagination workflow, ~40 actions). The tick track — the signature move of design 4, a row of small squares that fills in per step — was designed and only ever tested against the 2-4 step demo task used throughout this whole redesign effort ("upload the quarterly report..."). It does not degrade gracefully:

- At ~40 steps the dot row is one unbroken flex row with no wrap and no cap, so it overflows its container width. In the captured screenshots this pushes the sibling "Worked for 3m" duration text into a squeezed vertical single-character-per-line stack down the right edge of the panel — Adam's words, "it moves the whole dome around and breaks it."
- At ~20 steps (narrower panel) the row wraps onto a second line instead, which reads better but the dots are still individually meaningless at that count — nobody is going to count 20 identical green squares to know which step failed.
- Every real screenshot Adam sent was a genuine multi-step browser workflow: multiple tabs, retries, an explicit `action failed: Error: the control is covered or not visible` recovering mid-run. This is not an edge case; ordinary tasks on real sites regularly run 15-40+ actions. The demo task the whole design process was built and screenshotted against only ever had 2-3.

Not fixed. Adam explicitly said not to fix it now — capture it for later. Whoever picks this up needs a real design pass, not a patch: the tick track needs either a cap with an overflow affordance (a count past N, e.g. "12 more"), a different visual unit at high counts (a progress bar/percentage instead of discrete dots), or grouping (collapse consecutive same-kind actions). Screenshots referenced above are not preserved in the repo; ask Adam to resend if needed when this is picked up.

## Reviewer findings on this branch (2026-09-20, branch cursor/resume-integrity-c623)

Two rules in the section above were too loose and are corrected here; both fixes carry tests that were shown to fail against the previous code.

- Failure evidence now needs exactly *one* control whose `role\0name` matches the failed action. `role\0name` is not an identity — two "Email" boxes, or two rows of the same form, share it — so the first match could be a different control holding the intended value by coincidence, which settled a failure the run never resolved. Duplicates now keep the failure instead.
- `TYPE_AND_ENTER` is no longer cleared by value evidence: the field's value proves the typing landed, never that the Enter submitted anything, and a run may not report a submission it did not observe. `TYPE_TEXT` and `SELECT` are unchanged.
- Composer ownership is claimed in `startDictation()` *before* the `dictation:start` request is awaited, and released on both failure paths. The listening-state transition only claims a session this panel did not start. Reason: one failed chunk in `extension/offscreen.js` leaves the mic running and makes `state.dictation.status` flicker `listening → error → listening` inside a single session, which the old transition read as a new session and used to overwrite text the user had typed; claiming only after the await also dropped the first partial whenever the state broadcast beat the reply.
- A failed `startDictation()` releases only the ownership that press took (`tookOwnership`, captured before the claim). Unconditionally clearing it also cancelled a session this panel did not start — the global shortcut or its hands-free latch — for the rest of that session: its partials and its final transcript stopped reaching the composer. The unconditional release was correct only while the panel was the sole way to start dictation.
- The blocked message after a `TYPE_AND_ENTER` failure says the Enter was never observed ("the text landed in the field, but i never saw the Enter go through, so the submit is unconfirmed"), not that nothing on the page showed the change. The value is evidence the typing landed (that is why it no longer clears the failure), so the old sentence contradicted the field the user is looking at. `TYPE_TEXT`/`SELECT`/`CLICK` keep the original wording; `src/agent.ts` `unconfirmedMessage()` is the one place both blocked paths get their sentence from.
## Voice dictation: the quick-tap race, and plumbing that is never the user's error (2026-09-21, branch fix/dictation-voice)

Owner report: "Voice mouth doesn't work", with the panel's red line showing Chrome's own
`A listener indicated an asynchronous response by returning true, but the message channel closed before a response was received`.

- Reproduced headless against the built extension (Playwright's bundled Chromium). With the offscreen document already open, a `dictation:start` followed 5-10ms later by `dictation:stop` returned exactly that string as the start's reply; at 0ms (or with a fresh document) it returned `Offscreen document closed before fully loading.`, and the panel printed either verbatim (`title` empty). At 0ms the worker could also end up `status: 'listening'` with **zero** offscreen documents — a session state with no mic behind it.
- Root cause is the overlap, not the provider: hold-to-talk has no minimum hold, so `dictation:stop` runs while `dictation:start` is still awaiting `getUserMedia` in the offscreen document. The stop path always closed the document (`background.js` `closeOffscreen()` in a `finally`), which destroyed a reply the offscreen document still owed. Both transitions also interleaved their `state.dictation` writes, so whichever finished last won.
- Fix, three layers, no message is hidden: (1) `extension/offscreen.js`'s `stop()` waits for the in-flight `start()` (`startPromise`) before answering, so the caller can never close the document with a reply outstanding; (2) `extension/background.js` serializes start/stop/teardown through one `dictationTransition` queue, classifies Chrome's channel-gone strings (`CHANNEL_GONE`) as the extension's failure rather than the provider's, leaves nothing latched when the document vanishes, and a `dictation:stop` with no live session no longer messages a document that is not there; (3) `extension/panel.js` `humanError` gained one anchored `LOST_CHANNEL` case — "sash lost its connection to the browser before it could finish. try again, and reopen this panel if it keeps happening." — with the raw text kept on the element's `title`, per the error-line contract. Unrecognised text still passes through verbatim.
- The mic-permission tab is deduped (`chrome.tabs.query({url})`, then focus), and `dictation:permission-granted` now clears the latched failure it was asked about. It deliberately does **not** auto-retry the start: this is hold-to-talk, and a retry would open the mic with nobody holding the button. The grant page's own copy is what tells the user what to do next ("close this tab, then hold the mic button in the side panel to dictate").
- A failed start must not latch: the global shortcut's `onStart` now calls `cancelStart()` when the start it asked for did not open a mic, and the panel already drops `dictationSessionActive`/ownership on every failure path.
- Preserved deliberately: hold-to-talk, the session id created in `dictation:start` (a nonfatal chunk error must not steal the composer), and "a partial never overwrites what the user typed".
- Residual risk, not fixed: if `getUserMedia` never settles, the start hangs and the stop (and the queue behind it) waits with it. Chrome's getUserMedia settles (resolve or reject) in every observed case; a timeout here would reintroduce the dropped reply this fix exists to prevent.
- Not verified on a real machine: the mic permission prompt and a live microphone. All reproduction and coverage here is headless, with Chromium's fake audio device and a pre-granted extension origin (headless cannot show the grant prompt, so the grant-clearing path is unit-tested only).

## The open-panel command toggles (2026-09-21, branch feat/panel-toggle-command)

Asked for verbatim: "the command should open and close the panel depending on the current state. Right now it only opens it so I can close it with the same command." It now toggles. Base is `fix/dictation-voice` (PR #55, the voice fix); this is PR #56, stacked on it.

- Nothing in Chrome's side panel API reports whether the panel is open. `getOptions()` answers path/enabled and `getLayout()` answers which side it is docked to; neither says open. The only source is Chrome's own `sidePanel.onOpened` / `onClosed` events, so the open state is tracked from those and nothing else. Do not add a second guess at it.
- The panel belongs to a window, not a tab — the global panel shows on every tab of that window — so what is recorded is a set of window ids. The record lives in `chrome.storage.session`, never a module variable: an MV3 worker is suspended and restarted between presses and comes back with empty memory, and session storage survives exactly those restarts while dying with the browser, which is when the panel dies too. Do not move it into a module variable or into `chrome.storage.local`.
- A panel closed by hand with its X is recorded too. Chrome wakes the suspended worker to deliver `onClosed`, so the next press sees it closed instead of firing a `close()` that would no-op. Both events are required for this: `onOpened` alone cannot report a close, and a record that only ever grows turns the command into a no-op after the first manual close.
- `chrome.sidePanel.close` and both events are feature-detected, because they are newer than the manifest's declared `minimum_chrome_version` (118). Without them the command behaves exactly as before — open only. Do not drop those guards.
- Deliberately untouched: `openPanelOnActionClick` and the toolbar icon. The command toggles; the toolbar icon still only opens.
- The comment about preferring the tab the command listener hands you over an extra `chrome.tabs.query` round trip is preserved, now on the command listener that calls `toggleSidePanel` — its sibling — for the same reason: the query can resolve to a window that is no longer focused by the time it settles.
- Merge context: PR #55 (the voice fix) landed first, PR #56 (this) stacked on it, both merged into `main` together as `e1cdac3`, released as extension v0.4.17.
- Verification limit, plainly: the behaviour is covered by mocked-`chrome` unit tests plus the headless extension suite, and no human has watched the panel actually close on screen. The owner has told us twice not to open visible browser windows on his machine, so that confirmation must happen on his display or not at all.
